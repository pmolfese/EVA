# Maintaining saved recordings, settings, and replay

**Goal:** change a data contract while preserving the meaning of existing work.
Read [history and replay](history-and-replay.md) and
[data/lifecycle](data-and-lifecycle.md) first. The
[persisted-parameter recipe](recipes/persisted-parameter.md) provides an executable
missing-key and XML round-trip example.

## Identify the contract before editing

| Contract | Source to inspect | Failure a maintainer must prevent |
| --- | --- | --- |
| Processing script and operation names | [EVAProcessingScript](../../EVACore/Pipeline/EVAProcessingScript.swift) | Renamed raw values or parameters silently change which operations can replay. |
| Filter/settings dictionaries | [FilterViewModel](../../EVA/Filtering/FilterViewModel.swift), other models' `parameters` and `apply(parameters:)` | Live settings affect samples but never reach the saved script. |
| Interactive restoration and batch | [ReplaySettingsRestore](../../EVA/Pipeline/ReplaySettingsRestore.swift), [ProcessingCore](../../EVA/Pipeline/ProcessingCore.swift) | The same saved step means different things in UI replay and headless processing. |
| Learned payloads | [PayloadConsistency](../../EVA/Pipeline/PayloadConsistency.swift), [ReplayCompatibility](../../EVA/Pipeline/ReplayCompatibility.swift) | A matrix/template decodes but belongs to different channels or samples. |
| History/cache identity | [EVAHistory](../../EVA/Pipeline/EVAHistory.swift), [PipelineSnapshot](../../EVA/Pipeline/PipelineSnapshot.swift) | A stale output is reused under a changed request or history identity. |
| Reports/configuration | [EEGAnalysisModels](../../EVA/Analysis/EEGAnalysisModels.swift), simulation and rhythmicity models | A new required Codable field makes an old JSON document unreadable. |
| File export | [MFFExportWriter](../../EVA/IO/MFFExportWriter.swift), [MFFWriter](../../EVACore/IO/MFFWriter.swift) | Samples, timestamps, epochs, labels and provenance disagree after reopening. |

## Adding a field safely

Write down what an absent field means **before** choosing a decoder:

1. An optional report result can use `var result: Double? = nil`. Synthesized
   `Codable` decoding accepts a missing optional field. The UI must distinguish
   unavailable from a measured zero. The [metric recipe](recipes/analysis-metric.md)
   checks an old document with the new field removed.
2. A required value with a historical default needs explicit decoding such as
   `decodeIfPresent(Bool.self, forKey: .enabled) ?? false` in `init(from:)`, with
   the remaining fields decoded too. A stored property's default initializer
   does not generally make a missing nonoptional Codable key decode successfully.
3. A string parameter dictionary needs an explicit missing-key policy in
   `apply(parameters:)`. Some existing keys deliberately leave a current value
   unchanged. Do not assume all absent keys reset to defaults. Test restoration
   into both a fresh model and one previously configured differently.

For a new operation that did not exist historically, “missing means disabled”
is often the intended backward-compatible behavior. The tutorial's
`invertEEGPolarity` example tests this exact rule. Existing filter keys have
their own historical policies, pinned by
[`ParameterSerializationAuditTests`](../../EVATests/Pipeline/ParameterSerializationAuditTests.swift).
Changing those policies is a behavior change, not cleanup.

Record values at enough precision to reproduce their effect. Formatting to a
few significant digits can change a requested numeric parameter; compare the
serialized/restored value and resulting samples for your chosen parameter range.
Do not serialize a presentation label in place of the underlying mechanics.

## Renaming an enum case or changing a schema

Search for the serialized raw string, not just the Swift case name. A case may
be renamed in Swift while keeping its explicit old raw value; changing that
value needs a decoder alias or migration and fixtures for the old spelling.
Do not repurpose an old string to mean a different algorithm.

For a migration, define the input versions accepted, output version produced,
field mapping, defaults, invalid cases, and whether the migration is repeatable.
Keep a small old-format fixture that is not generated by the new serializer.
Test old → current decode, current encode → decode, unknown/unsupported values,
and malformed payloads. Preserve the original user file while testing; export
to a new destination. A successful JSON/XML parse proves syntax, not compatibility.

Backward compatibility (new code reads old work) and forward compatibility (old
code reads new work) are separate. An old application may ignore a newly added
filter parameter and replay different samples. Before shipping a new parameter,
decide how supported readers detect required capabilities or reject unsupported
scripts; stamping an app version alone does not enforce that policy. The tutorial
patches are exercises and are not a completed cross-version release policy.

## Samples, caches, and learned state

Changing samples must change sample identity and invalidate dependent results.
Use `MFFSignalData.replacingSamples` for the same timeline; use the explicit
timeline reconstruction path when changing sample count/events/epochs. Event-only
changes need event-sensitive request keys even when sample revision is preserved.

A saved ICA unmixing matrix or artifact template is not portable merely because
its dimensions fit. Check channel order, preprocessing/reference, geometry,
sampling/timing assumptions, and payload digests where used. Read the payload's
own version/validation code and the consumer together. Test incompatible inputs
and confirm the UI/batch path reports the reason rather than silently proceeding.

`PipelineSnapshot` is an in-session cache of outputs/decisions. It intentionally
does not duplicate all parameter dictionaries. For a new field, trace parameter
restoration from the history path as well as output restoration; do not create
two independent settings sources that can disagree.

## Replay and batch maintenance

Run the same script on the same synthetic input through live application,
restored settings, and `ProcessingCore` where supported. Compare samples and
metadata, not just whether the calls return. Confirm unsupported or decision-
requiring steps remain explicit in the outcome; never claim a full replay when
only an automatic prefix ran.

Inspect [BatchPrefixPlanner](../../EVA/Pipeline/BatchPrefixPlanner.swift),
[BatchPreflight](../../EVA/Pipeline/BatchPreflight.swift),
[BatchDecisionPolicy](../../EVA/Pipeline/BatchDecisionPolicy.swift), and
[BatchCheckpoint](../../EVA/Pipeline/BatchCheckpoint.swift) before changing batch
semantics. Existing-prefix reuse, per-file decision dropping, and checkpoint
resume are separate policies. A changed operation or input must not be mistaken
for already completed work just because the output filename is unchanged.

## A compatibility check for a real change

1. Capture a small old file/script before editing and record its intended result.
2. Add tests for missing keys, non-default values, invalid values and round-trip.
3. Compare live versus replay results and check invalidation/history restoration.
4. Export processed data to a fresh MFF, reload it, and compare sample shape,
   units, labels, events, epoch boundaries and script/payloads.
5. Exercise batch/preflight/checkpoint behavior if the changed operation can run
   there. Inspect reported remaining steps and refusal/skip reasons.
6. Describe backward and forward compatibility, migration requirements, and
   scientific output changes in the change/release notes.

Start with `FilterReplayTests`, `ParameterSerializationAuditTests`,
`EVAProcessingScriptXMLTests`, `PayloadConsistencyTests`, `ReplayCompatibilityTests`,
`PipelineSnapshotTests`, `BatchPrefixPlannerTests`, `BatchCheckpointTests`, and
the affected reader/export tests. Confirm their actual fixtures/backend needs in
[testing](testing.md). An independent exercise is to remove one optional field
from a current report JSON and explain why it decodes differently from removing
a required nonoptional field.
