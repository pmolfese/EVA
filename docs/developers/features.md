# Feature → code → tests

Use this map when you know what the user wants to change but do not yet know
which files own it. The UI entry point is not necessarily the place
to implement computation. Follow the state owner to the engine and then inspect
the named tests. A test listed here is a starting point, not a claim of complete
coverage. Read [data and lifecycle](data-and-lifecycle.md) before changing shared
state and [the source inventory](source-inventory.md) for every in-scope file.

## How to use one row

For a new filter option, open `FilteringViews`, find the binding, follow it into
`FilterViewModel`, then identify where `apply` snapshots it and calls the engine.
Inspect `parameters` and `apply(parameters:)` before adding the control. Run the
existing filter replay tests, then add a non-default round-trip case and a legacy
missing-key case. See the [persisted parameter recipe](recipes/persisted-parameter.md)
for the complete exercise.

For UI-only work, identify the lifetime first: sheet, recording window, or app
preference. For sample-changing work, follow invalidation, history, serialized
parameters, interactive replay, and batch. For format readers, check units,
metadata, sidecars, export/reimport, and all consuming targets.

The [subsystem pages](subsystems/README.md) explain surrounding files. The
[inventory maintenance check](documentation-maintenance.md) detects missing or
stale entries; semantic accuracy still requires reading call sites.
